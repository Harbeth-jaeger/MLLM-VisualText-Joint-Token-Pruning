# MLLM Visual-Text Joint Token Pruning

探索多模态大语言模型（MLLM）中的视觉与文本 token 联合剪枝，在减少计算开销的同时尽可能保持任务性能。



# 研究问题

**本章回答“在××场景，由于××，因此现实需要××，但是暂时没人做××，所以我来做××”**

## idea 定位

在长多模态输入中，视觉与文本共同竞争有限的上下文和计算预算；二者的信息存在互补、重复和依赖关系。现有方法大多只优化视觉 token，无法根据不同样本的实际信息结构，在两种模态之间动态分配预算。因此需要研究一种面向任务、跨模态协调的联合 token 选择机制。

## 研究意义/动机

### 一、为什么研究这个问题

#### 1. MLLM输入正从"单图＋短问题"转向长多模态上下文

传统 VQA 通常是：

* 一张图片；
* 一个十几到几十 token 的问题；
* 一个较短答案。

在这种场景下，视觉 token 可能有几百甚至几千个，而文本只有几十个。因此，过去大量工作只剪视觉 token 是合理的。

例如 FastV、LLaVA-PruMerge、SparseVLM 等工作主要围绕视觉 token 冗余展开；SparseVLM也明确指出，视觉 token 通常占据显著计算开销，而且相较文本 token 信息密度更稀疏。[GitHub](https://github.com/chenllliang/FastV?utm_source=chatgpt.com)

但是，现在 MLLM 的输入场景正在变化：

* 多页图文文档理解；
* 图表、表格与长说明文本联合分析；
* 多图问答；
* Visual RAG；
* 网页、幻灯片和论文阅读；
* GUI/网页 Agent 的长轨迹；
* 多轮对话中累积的图像和文本历史；
* 多文档、多图片交叉检索与推理。

MMLongBench已经用 Visual RAG、many-shot ICL 等任务评测8K到128K的多模态上下文，并把视觉 patch 和文本 token 统一计算输入长度。这说明"视觉和文本共同形成长上下文"已经不是人为构造的边缘情况。[zhaowei-wang-nlp.github.io](https://zhaowei-wang-nlp.github.io/MMLongBench-page/?utm_source=chatgpt.com)

因此，过去的假设：

N\_v \\gg N\_t

不再总是成立。现实中可能出现：

N\_v \\approx N\_t

甚至在视觉 token 已经过一轮压缩之后：

N\_t > N\_v

这时继续只剪视觉 token，收益会逐渐触顶。

---

#### 2. 两种模态共同消耗同一个 LLM 的计算资源

经过 visual encoder 和 projector 后，视觉 token 通常会和文本 token 拼接，统一输入 LLM：

X=[X\_v;X\_t]

因此，LLM 实际处理的序列长度是：

N=N\_v+N\_t

Transformer self-attention 的主要计算量近似随序列长度平方增长：

O(N^2D)

而 FFN、投影和 KV cache 等开销也会随 token 数增加。

所以从 LLM 的视角看，计算瓶颈并不关心一个 token 原来来自图像还是文本。只剪视觉 token，本质上是在优化：

N\_v

但真正决定 LLM 计算量的是：

N\_v+N\_t

例如：

* 原始输入：2000个视觉 token＋200个文本 token；
* 剪掉75%视觉 token：500＋200＝700；
* 此时文本已经占总输入的约29%。

如果场景变成：

* 2000个视觉 token＋2000个文本 token；
* 剪掉75%视觉 token：500＋2000＝2500；

那么即使视觉剪枝很激进，总长度仍然很长，文本成为新的主要瓶颈。

因此，visual-only pruning 在长文本、多文档或视觉已经高度压缩的场景中，会出现明显的**边际收益递减**。

---

### 二、为什么不能把现有 visual 和 text prune 简单拼接

这是你论文最重要的研究意义所在。

#### 1. Visual-only方法默认文本全部重要

大部分视觉剪枝方法的隐含策略是：

\\text{Keep all text tokens, prune visual tokens only}

这在短问题 VQA 中成立，因为问题本来就很短，剪文本带来的收益有限、风险却很高。

但在长文本输入中，文本也可能包含大量冗余：

* 文档中与当前问题无关的段落；
* 重复说明；
* RAG检索得到但最终无用的文档块；
* few-shot示例中的冗余描述；
* Agent历史中已经失效的状态；
* 图片附近与当前问题无关的标题、脚注和说明；
* 对视觉信息的重复文字描述。

这时，"所有文本 token 都比视觉 token 重要"不再是合理假设。

---

#### 2. 视觉和文本的重要性具有相互依赖性

设图片里写着：

> Revenue increased by 12% in 2025.

配套文本也写着：

> The company reported a 12% revenue increase in 2025.

如果视觉中的数字和文本完全重复，那么保留其中一个证据可能就够了。

但如果文本写的是：

> As shown in Figure 3, the growth mainly came from the overseas business.

而图中才包含各业务板块的具体数值，那么文本和图像是互补的，缺一不可。

因此，重要性不应分别计算为：

I(v\_i),\\qquad I(t\_j)

而应当考虑条件重要性：

I(v\_i\\mid T,q)

I(t\_j\\mid V,q)

也就是说：

* 如果文本已经完整表达某个信息，对应视觉 token 的边际价值可能下降；
* 如果图像已经清楚呈现某项信息，对应文本描述可能可以压缩；
* 如果一个文本 token 用来指代某个局部图像区域，那么二者必须同时保留；
* 如果删除文本中的实体、约束词或关系词，视觉 token 即使保留也可能失去解释依据。

所以这个问题不是两个独立的 top-**k**：

S\_v=\\operatorname{TopK}(I\_v),\\quad S\_t=\\operatorname{TopK}(I\_t)

而是一个联合选择问题：

(S\_v,S\_t) = \\arg\\max\_{S\_v,S\_t} U(S\_v,S\_t;q)

这正是"joint"存在的必要性。

---

#### 3. 固定模态比例无法适应不同样本

不同任务对两种模态的依赖非常不同：


| 任务                 | 主要证据             | 理想预算倾向                   |
| -------------------- | -------------------- | ------------------------------ |
| 图片颜色识别         | 图像                 | 多保留视觉 token               |
| OCR问答              | 图像中文字＋问题约束 | 保留关键视觉区域和关键词       |
| 图文文档问答         | 跨页文字、图表、说明 | 动态分配                       |
| 图表推理             | 图表结构＋文本问题   | 两者都不能过度剪               |
| 长提示词下的图片问答 | 图片＋少量有效文本   | 删除无关文本段落               |
| Visual RAG           | 少量相关图文块       | 同时过滤无关图片和文本         |
| 多轮Agent轨迹        | 当前截图＋历史状态   | 删除过期历史，保留当前视觉状态 |

所以不存在一个适用于所有样本的固定比例，例如：

80\\%\\text{视觉预算}+20\\%\\text{文本预算}

真正有意义的联合剪枝应当做到：

(B\_v^{(x)},B\_t^{(x)}) = f(x,q)

即针对每个样本动态确定视觉与文本预算，并满足：

B\_v^{(x)}+B\_t^{(x)}\\le B

这可以被称为：

* sample-wise budget allocation；
* modality-aware token budgeting；
* cross-modal adaptive pruning。

## 适用场景

### 场景一：长多模态文档理解

例如输入一篇带有：

* 多页正文；
* 多张图表；
* 表格；
* 图注；
* 附录；

的论文或财报，然后提问：

> 2025年利润率下降主要来自哪个业务板块？图表和正文给出的解释是否一致？

这里既有大量视觉 token，也有大量文本 token，而真正相关的信息可能只存在于：

* 一张利润率图；
* 两段正文；
* 一个图注；
* 问题中的几个核心约束。

只做视觉剪枝可能误删关键图表，也无法删除大量无关正文；只做文本剪枝则可能忽略正文和图表之间的对应关系。

联合剪枝的目标是保留一个**最小但充分的跨模态证据集**。

---

### 场景二：Visual RAG

Visual RAG可能检索出多个包含文字、图片、表格和截图的页面。

检索阶段通常只能保证候选内容“可能相关”，不能保证每个 token 都有用。输入 MLLM 后可能包含：

* 若干无关图片；
* 图片中的无关区域；
* 无关文本块；
* 多个候选页面之间重复的信息。

如果只剪视觉 token，检索回来的无关文本仍然全部进入LLM；如果只剪文本，则可能留下大量无关视觉 patch。

联合剪枝可以看作对检索结果进行细粒度的**跨模态二次过滤**。

---

### 场景三：多图片＋长问题/长背景

例如医学影像、工业检测或长篇视觉推理：

* 多张不同角度的图片；
* 较长的案例背景；
* 多个限制条件；
* 一个需要跨图比较的问题。

这里文本不能简单按长度剪，因为诸如“不考虑左侧异常”“仅比较治疗后影像”之类的短片段可能非常关键；视觉也不能按统一比例剪，因为不同图片的重要性不同。

联合方法需要同时回答：

* 哪一张图重要；
* 图中的哪个区域重要；
* 哪一段背景重要；
* 哪个文本约束决定视觉证据的解释方式。

---

### 场景四：多模态Agent的历史压缩

GUI Agent、Web Agent或具身Agent可能不断累积：

* 历史截图；
* OCR文本；
* 用户指令；
* action history；
* 工具返回值；
* 中间推理状态。

这些内容最终共同占用上下文和 KV cache。

例如Agent已经从页面A跳转到页面B，那么：

* 页面A的大部分视觉 token可能过期；
* 但页面A中记录的订单号仍然重要；
* 页面B当前截图非常重要；
* 某些重复的工具返回文本可以删除。

这种场景本质上就要求跨模态、时序化的联合上下文压缩。
